# The hand-checkable data set

`db/tests/fixture.sql` is deliberately tiny: three relief centres, two
resources, one zone. Every number the SQL tests assert can be worked out on
paper from this page, which is the point. A test suite whose expected values
can only be obtained by running the code proves that the code agrees with
itself.

It is reloaded before **every** test, so no test can see another's writes.

## The data

**Resources**

| id | name | unit |
|---|---|---|
| 1 | Blankets | units |
| 2 | Water Cans | litres |

**Relief centres**

| id | name | latitude | longitude |
|---|---|---|---|
| 1 | Guwahati Relief Centre | 26.144500 | 91.736200 |
| 2 | Delhi Relief Centre | 28.613900 | 77.209000 |
| 3 | Chennai Relief Centre | 13.082700 | 80.270700 |

**Zone** — one, `Guwahati Flood Zone`, at **26.144500, 91.736200**: exactly the
coordinates of centre 1. That is chosen, not incidental. It makes the distance
ordering unambiguous, so "nearest first" has a single correct answer and a
test that depends on it cannot pass by luck.

**Stock**

| centre | resource | quantity | low threshold |
|---|---|---|---|
| 1 Guwahati | Blankets | 10 | 5 |
| 2 Delhi | Blankets | 40 | 5 |
| 3 Chennai | Blankets | 100 | 5 |
| 1 Guwahati | Water Cans | 60 | 20 |

**Total Blankets in the system: 10 + 40 + 100 = 150.**

## Distances from the zone

Computed by `fn_haversine_km`, and checkable against an atlas:

| centre | km from the zone |
|---|---|
| 1 Guwahati | **0** — the zone sits on top of it |
| 2 Delhi | **1459** |
| 3 Chennai | **1882** |

So the allocator's draw order is always **1 → 2 → 3**.

## Worked examples

### A request for 45 Blankets

Centre 1 holds 10, centre 2 holds 40.

```
take min(10, 45) from centre 1  ->  35 still outstanding, centre 1 now 0
take min(40, 35) from centre 2  ->   0 still outstanding, centre 2 now 5
centre 3 is never reached
```

Expected: **45 allocated, 2 legs, status `fulfilled`**, and stock left at
**0 / 5 / 100**. That is exactly what `040_proc_allocate_nearest_first`
asserts.

Centre 1 falling to 0 is below its threshold of 5, so **one** `StockAlerts`
row is raised — and only one, however much further it falls.

### Cancelling that request

Every active allocation is released and the stock goes back exactly as it
was drawn:

```
centre 1 gave 10  ->   0 + 10 =  10
centre 2 gave 35  ->   5 + 35 =  40
centre 3 gave  0  -> 100 + 00 = 100
```

Expected: **45 released across 2 legs**, stock restored to **10 / 40 / 100**,
both allocations still present with status `released` (not deleted), and the
request `rejected`. `041_proc_cancel_returns_stock` asserts this.

### A request for 100 Blankets

```
10 from centre 1, 40 from centre 2, 50 from centre 3  ->  100, fulfilled
```

### A request for 200 Blankets

Only 150 exist, so it is **partially** fulfilled: 150 allocated across 3 legs,
50 outstanding, status stays `allocated` rather than `fulfilled`. Partial
fulfilment is normal, not an error.

## Why these numbers

- **10, 40, 100** are distinct and non-round-trippable: if the allocator drew
  from the wrong centre, or in the wrong order, the resulting totals could not
  coincidentally match.
- **The zone sits on centre 1** so the nearest centre is unarguable.
- **Centre 1 holds the least**, so the very first draw exhausts a centre and
  forces the allocator onto a second one. An ordering bug that only shows up
  when a centre runs dry is caught by the smallest possible test.
- **Water Cans exist but are never allocated**, so a query that forgets to
  filter by resource shows up immediately: the totals go wrong by 60.

## The large seed

Generated by `db/seed/generate.py` from a fixed seed, with its totals written
to `db/seed/MANIFEST.json`:

| | |
|---|---|
| relief centres | 30, across 21 cities and 16 states |
| resources | 45 |
| zones | 12 |
| stock rows | 596, of which 82 open at zero |
| total units held | 108,150 |
| stock history rows | 2,345 |
| requests | 600, all `pending` |

Nothing is pre-allocated. Allocation is what the demo, the tests and the
concurrency scripts *do*, and a seed that had already run it would hide
whether it works.

Regenerate with `python3 db/seed/generate.py`; `--check` verifies the
committed files are current without rewriting them.
